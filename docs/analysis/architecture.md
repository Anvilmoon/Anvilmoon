# Architecture

## Repository layout

```
www/                         the game, published as-is by Vercel on every push to main
  index.html                 the entire client: CSS + markup shell + all JS (3,550 lines)
  config.js                  runtime settings (server address, dev flag, OAuth providers)
  sw.js                      service worker: offline cache, keyed by VERSION
  manifest.webmanifest       PWA manifest (installable, standalone)
  vercel.json                /api rewrite to Supabase, CSP and caching headers
  fonts/ icons/              self-hosted woff2 fonts (VT323, Pixelify Sans, Jacquarda Bastarda 9, Atkinson) and PNG icons
supabase/
  schema.sql                 the three tables
  sql/am_records.sql         SQL functions: Records boards, smith's hall, extension endpoints
  functions/api/index.ts     the whole game server (Edge Function, Deno)
  functions/api/types.ts     blade type -> weight class map, generated from the client's TYPES table
tools/
  devproxy.js                local test proxy (static www + /api forwarded to a local function)
  export.py, migrate.py      one-off scripts that moved data off the old PC server
```

There is no `package.json`, no bundler, no tests, no CI and no `supabase/config.toml`.

## Runtime topology

```
Browser (index.html, localStorage save, service worker)
   |  same-origin fetch /api/...
   v
Vercel (static hosting for www/, fra1 edge)
   |  rewrite /api/:path*  ->  https://macpadytmqfjmczimoid.supabase.co/functions/v1/api/:path*?forceFunctionRegion=eu-west-2
   v
Supabase Edge Function "api" (Deno, npm:postgres, npm:jose)
   |  one connection (max: 1), every request in one transaction
   v
Postgres: am_state (1 row, shared blob) · am_saves (one row per account) · am_history (save snapshots)
          functions am_records(), am_x_records(), am_x_hall()
```

- Because `/api` is rewritten on the same origin, the strict CSP (`connect-src 'self'`) still allows API
  calls. `config.js` sets `ANVILMOON_SERVER = location.origin`.
- Discord/Google sign-in goes through Supabase Auth (`ANVILMOON_AUTH.url`), but `providers: []` in
  `config.js`, so those buttons are hidden in production.
- `index.html` has Capacitor hooks (haptics, Android back button, no service worker when native), so a
  native wrapper was planned or exists outside this repo.

## Deployment

- **Client:** push to `main` → Vercel publishes `www/`. Bump `VERSION` in `www/sw.js` with every change or
  installed players keep the old cached shell (assets are cache-first; navigations are network-first).
- **Server:** deployed separately with the Supabase CLI (not automated here). When blade types change in
  `index.html`, `types.ts` must be regenerated by hand (there is no script for it in the repo) and the
  function redeployed. Records logic lives in SQL so it can change without redeploying the function.

## Request lifecycle (server)

Every request (`handle()` in `index.ts`):

1. Normalise the path to start at `/api` (works whether called as `/api/...` or `/functions/v1/api/...`).
2. Parse JSON body (limit 3 MB).
3. **Fast path:** `GET /api/poll?ver=N` reads only `ver, next_due` from `am_state`. If `ver` is unchanged and
   nothing is due yet, it answers `{ver}` without a transaction.
4. Otherwise: `BEGIN`, `SELECT ... FROM am_state WHERE id=1 FOR UPDATE` (a global lock), load the whole blob
   into the module variable `db`.
5. `tick()`: run gift campaigns, settle expired auctions, time out arena rounds, drop finished matches,
   swap 20-second ranked-queue waiters to a bot match, drop stale queue entries, hourly prune of sessions and
   throttles. There are no cron jobs: everything time-based happens at the start of whichever request
   arrives next, and `next_due` tells the poll fast path when that is.
6. `api()` routes the request.
7. If anything was marked dirty, write the whole blob back, `ver++`, recompute `next_due`. `COMMIT`.

Consequence: every non-fast-path request in the game is serialised behind one row lock, and each one reads
and rewrites the whole shared blob.

## Client persistence and cloud sync

- `A` is the whole save. `save()` stamps `A.at`, recomputes `A.wealth` and `A.hall` (the public hall
  summary), increments `A.rev`, writes `localStorage['anvilmoon-save-v1']`, and calls `queueSave()`.
- `queueSave()` debounces 500 ms, then `pushSave()` sends `PUT /api/save {save: A, base: A.base}`.
- **Optimistic concurrency:** the server's `am_saves.rev` must equal `base`. Otherwise it answers 409 with the
  server copy; the client runs `mergeSaves()` and retries (up to 3 times).
- `mergeSaves(a, b)`: the newer (`at`) save wins, then from the older one: union of `claimed`/`mailSeen`, max
  of `serial`/`totalForged`/`forged`, union of classes, and any **owned** blade missing from the newer save is
  added. The same blade in both is matched by fingerprint `type|len|grade|t`, and the later status change
  (`su` timestamp) wins.
- `syncSave()` after login decides between: push (server empty), adopt (device empty, or device is an
  unmodified copy of an older server save), or merge.
- Other tabs: a `storage` event with a higher `rev` is adopted (deferred via `PENDING` while forging/revealing).
- `flushSave()` on `visibilitychange`/`pagehide` uses `fetch(..., {keepalive:true})`.
- The server snapshots the previous save into `am_history` at most every 10 minutes and keeps the last 12.
- Manual backup: "Copy backup code" is `btoa(JSON(A))`; restore replaces `A`.

## Live updates

There are no websockets. `pollLoop()` calls `GET /api/poll?ver=N`:

- every 8 s normally, every 1.5 s while queued or in a duel, paused while the tab is hidden (unless a duel is on);
- the answer carries `mail` (a signature of the player's mail ids), `ah` (auction revision counter), `pvp`
  (current or last match view) and the new `ver`;
- a change in `mail` triggers `GET /api/mail`; a change in `ah` triggers `GET /api/ah`; a changed `pvp` is
  handed to `arenaUpdate()`.

Also: `fetchMail()` every 60 s; `GET /api/pvp/state` every 1 s while queued; records refetched when the
Records tab is open and older than 10 s.

## Sign-in

- Username + password (scrypt, 64-byte key, per-user salt) → random 32-byte bearer token, stored hashed
  (sha256) in `db.sessions`, valid 30 days. Client keeps it in `localStorage['anvilmoon-token']`.
- Recovery code: 16 chars from an unambiguous alphabet, shown once, stored as sha256. Username + code sets a
  new password and signs out every device.
- OAuth (disabled in prod config): Supabase Auth redirect → access token in the URL hash → `POST /api/oauth`
  verifies the JWT against Supabase JWKS (fallback: ask `/auth/v1/user`), then links or creates an account.
- Throttles live in the shared blob: 10 auth calls/min per IP, 8 logins/10 min per username, 3 registrations
  per hour per IP and 60 per hour overall, 5 recoveries/hour per username.
- If `SERVER` is set and the player is not signed in, the game shows only the welcome/sign-in screen
  (`needAcct()`). A public Smith's hall (`/?smith=Name`) can be viewed signed out.

## Security model (summary)

The client is authoritative for nearly everything: coin, materials, blades and their stats live in a save
the client writes wholesale. The server only clamps blade fields (`cleanBlade`) when a blade enters the
auction house or arena, and HTML-sensitive characters are stripped from all API responses (`scrub()`) and
names (`cleanName`/`safeName`). See [observations.md](observations.md) for what that allows.

Web hardening is good: strict CSP (no external origins), `X-Frame-Options: DENY`, `nosniff`,
`no-referrer`, API responses `no-store`, tables have RLS enabled with all grants revoked from `anon` and
`authenticated` (only the function's own DB connection can touch them).
